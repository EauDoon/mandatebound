# MandateBound v1.2

## Result

MandateBound v1.2 adds an exact-byte AP2 Evidence Pack and a deterministic dispute evidence resolver. A small transaction can now move through:

```text
pack -> verify -> render
```

The pack preserves the Mandates, Checkout version, Receipts, caller-owned verification pins, and imported revocation snapshots. Independent verification requires an expected Pack digest retained outside the Pack, recomputes every stored digest, and reruns the AP2 integrity gates. Rendering produces a metadata-only review timeline that omits the raw evidence bytes.

The resolver answers one bounded question:

> Do the supplied AP2 dispute artifacts pass this pinned integrity profile for the same transaction?

The resolver emits `evidence_verified` or `unresolved`. Evidence Pack verification emits `verified` or `unresolved`. None of these states decides a dispute, claim, refund, chargeback, liability question, or legal right.

## Pinned profile

The v1.2 profile is pinned to:

- AP2 release `v0.2.0`;
- immutable upstream commit `b4587ac1d055888a73b4b21750973cffba961793`;
- closed Mandate types `mandate.checkout.1` and `mandate.payment.1`;
- direct Human Present SD-JWT Mandates and Human Not Present Delegate SD-JWT chains;
- terminal Delegate SD-JWT types `kb+sd-jwt` and `kb-sd-jwt`;
- the required open Checkout constraint `checkout.line_items`;
- the required open Payment constraint `payment.reference`; and
- Receipt references named `sha256-terminal-compact-jws`.

The Mandate chain profile is:

```text
ap2-v0.2.0-mandate-chain+b4587ac1d055888a73b4b21750973cffba961793
```

The protocol release, Mandate schema suffix, and MandateBound package release are separate version layers. v1.2 does not reinterpret AP2 `.1` Mandates as a new upstream schema.

The `releaseVersion` field of a resolution, Evidence Pack, or Pack verification report names the format release `1.2.0`, exported as `AP2_DISPUTE_FORMAT_RELEASE`. It stays `1.2.0` in every later package release, so a package release never invalidates a retained Pack through its label, and new artifacts keep matching the `schemas/v1.2` constants. A Pack retained from 1.2.0 keeps its format label and Pack digest and still matches its retained anchor. Verification re-derives the resolution from the embedded evidence under the current gates, though: since 2.0.0, delegated Mandate payloads require `exp`, so a 1.2.0 Pack whose delegated Mandate payload has no `exp` verifies as `unresolved` with `AP2_PACK_RESOLUTION_UNRESOLVED`, while `digestValid` and `anchorMatched` stay true. The HTML timeline labels the field "Pack format". See [ADR 0003](adr/0003-version-layers.md).

## Mandate verification

Human Present evidence may contain one issuer-signed closed SD-JWT. Human Not Present evidence uses the AP2 Delegate SD-JWT grammar:

```text
root-segment ("~~" delegate-segment)*
```

Every segment is verified from the pinned root key through the preceding `cnf.jwk`. Intermediate hops must remain open. The terminal hop must be closed, must carry the expected audience and nonce, and must not contain another `cnf` key. Each hop contains exactly one `sd_hash` or `issuer_jwt_hash` binding.

A trailing plain `kb+jwt` is not an AP2 v0.2.0 Delegate SD-JWT chain and fails closed in the v1.2 resolver profile. The older additive UCP/AP2 adapter remains available for v1.1 compatibility but is not used by this resolver.

For autonomous Checkout Mandates, the verifier evaluates the required `checkout.line_items` constraint against the exact Checkout JWT. It evaluates `checkout.allowed_merchants` against the merchant in that bound merchant-signed Checkout JWT. If the caller also supplies an expected-merchant pin, the signed merchant must match that pin. For autonomous Payment Mandates, it verifies `payment.reference` against the AP2 `sd_hash` of the associated open Checkout Mandate, and since 2.1.0 evaluates the other payment constraints the pinned reference shopping agent emits against the closed Payment Mandate:

| Constraint | Open Mandate | Evaluated against | Rule |
| --- | --- | --- | --- |
| `checkout.line_items` | Checkout (required) | bound Checkout JWT `line_items` | every requirement is met from the revealed acceptable items |
| `checkout.allowed_merchants` | Checkout | bound Checkout JWT `merchant.id` | equals the `id` of a revealed allowed entry |
| `payment.reference` | Payment (required) | associated open Checkout Mandate | `conditional_transaction_id` equals its AP2 `sd_hash` |
| `payment.amount_range` | Payment | closed `payment_amount` | same `currency`, and `min <= amount <= max` inclusive; `min` is optional |
| `payment.allowed_payees` | Payment | closed `payee.id` | equals the `id` of a revealed allowed entry |
| `payment.allowed_payment_instruments` | Payment | closed `payment_instrument.id` | equals the `id` of a revealed allowed entry |
| `payment.allowed_pisps` | Payment | closed `pisp` | `legal_name`, `brand_name` and `domain_name` all equal one allowed entry; a missing `pisp` fails |

A constraint that does not hold reports `AP2_CONSTRAINT_FAILED`. An amount range whose `currency` is not a non-empty string, whose `max` or `min` is not a safe integer in minor units, or whose `min` exceeds `max` reports `AP2_CONSTRAINT_INVALID`; that includes a major-unit string such as `"25.00"`. Payees match by `id` only, as `checkout.allowed_merchants` does, so the SDK's name-and-website fallback is not accepted. A malformed closed field fails the constraint and never throws. A `payment.*` constraint inside an open Checkout Mandate stays `AP2_CONSTRAINT_UNSUPPORTED`. `payment.budget` and `payment.agent_recurrence` need cumulative spend history the evidence does not carry, and `payment.execution_date` has no fixed format at the pinned commit, so these and every unknown type stay `AP2_CONSTRAINT_UNSUPPORTED` and produce `unresolved`. `AP2_DISPUTE_CONSTRAINT_SUPPORT` exports both lists, and the conformance declaration publishes them as `disputeProfile.evaluatedConstraints` and `disputeProfile.failClosedConstraints`. The exported `verifyAp2MandateChain` (`@oonyl/mandatebound/ucp-ap2`) applies the same evaluation and the withheld-disclosure checks below, so its `upstreamValid` changes in the same cases. The v1.1 `verifyAp2Mandate` adapter still rejects every `payment.*` type it did before.

The closed Payment Mandate must contain a transaction ID, a payee with `id` and `name`, an integer amount with a currency, and a payment instrument with `id` and `type`.

### Withheld constraint disclosures

The presenting agent chooses which issuer-signed SD-JWT disclosures of the open Mandate to reveal before it signs the terminal hop. Since 2.1.0 withholding part of a constraint can no longer widen the open Mandate's constraints. The resolver reports `AP2_CONSTRAINT_DISCLOSURE_WITHHELD` and leaves the resolution `unresolved` when:

- an entry of the open Mandate's `constraints` list is an undisclosed `{"...": digest}` placeholder (reported at `token.claims.constraints`);
- a constraint entry carries an `_sd` digest whose disclosure is not presented, for example one hiding the optional `min` of `payment.amount_range`;
- an entry of a `checkout.line_items` requirement list is undisclosed; or
- a requirement's issuer-signed `acceptable_items` list had elements but none of them is revealed (the last three reported at that constraint).

RFC 9901 lets an issuer add decoy digests to arrays and objects alike, and a decoy cannot be told apart from a withheld disclosure. A decoy in one of these positions therefore also leaves the resolution `unresolved`: a deliberate fail-closed result, so an issuer should keep decoys out of constraint lists, constraint entries and line-item requirement lists. Undisclosed `_sd` digests elsewhere in the open Mandate payload are not checked, because failing closed there would reject every decoy-bearing payload; one could hide a pre-set field such as a payee, amount or payment instrument from the inheritance check, which the [threat model](THREAT_MODEL.md#residual-risks) lists as a residual risk.

AP2 matches line items only against the revealed acceptable items, so a partial reveal is evaluated against what it reveals. An issuer-signed literal empty `acceptable_items` list is not withheld and keeps the SDK's any-item meaning. An allowed-merchant or allowed-payee list with no revealed element already fails with `AP2_CONSTRAINT_FAILED`, and undisclosed alternative `delegate_payload` elements remain legitimate. Evidence redacted with the official SDK's `MandateClient.present(claims_to_disclose=...)` drops every acceptable-item disclosure, so it now resolves `unresolved` where it used to pass through the wildcard; the SDK's default presentation reveals them and is unaffected.

## Required dispute evidence

One positive resolver result requires exact compact bytes for:

1. Checkout Mandate
2. Checkout Receipt JWT
3. Payment Mandate
4. Payment Receipt JWT

The resolver also verifies the merchant signature and bounded pinned UCP Checkout shape of the Checkout JWT disclosed by the closed Checkout Mandate. Parsed or reserialized JSON is not substituted where a signature, disclosure digest, or reference covers an exact representation.

The caller supplies one verification plan outside every source response. It contains historical public-key snapshots, caller-owned key-source digests, expected issuers, expected audiences and nonces, the expected Checkout JWT when known, algorithm allowlists, and an explicit `asOf` time. Private keys do not belong in the plan. A source cannot self-authenticate by supplying its own trust anchors.

## Integrity gates

The resolver verifies:

- strict compact serialization, bounded token size, and canonical base64url;
- root and delegated Mandate signatures;
- historical key eligibility, including capture time and validity window;
- AP2 disclosure integrity, delegation key continuity, audience, nonce, and time;
- that no open-Mandate constraint entry, line-item requirement, or whole non-empty acceptable-item list is withheld behind an undisclosed placeholder, and no constraint entry hides a field behind an undisclosed `_sd` digest;
- required open constraints and closed Mandate fields;
- the merchant signature and bounded shape of the Checkout JWT;
- equality between the exact Checkout JWT hash, `checkout_hash`, `transaction_id`, and query key;
- Checkout and Payment Receipt signatures, issuers, times, and pinned schemas;
- Checkout Receipt reference to the terminal closed Checkout Mandate JWS; and
- Payment Receipt reference to the terminal closed Payment Mandate JWS.

An authentic AP2 `Error` Receipt remains valid evidence when its signature, schema, issuer, and reference are valid. It records a rejection. It does not determine why a broader dispute should be resolved.

## Receipt reference profile

The exact Receipt reference formula is:

```text
base64url(SHA-256(ASCII(terminal compact JWS before the first "~")))
```

This matches the pinned AP2 v0.2.0 SDK behavior and is named `sha256-terminal-compact-jws`. The verifier does not try alternate representations until one succeeds. A different interpretation requires a new named profile and fixtures.

## Evidence Pack

`MandateBoundAp2EvidencePack/v1` contains:

- the pinned release and profile;
- transaction ID, `asOf`, and creation time;
- the caller-owned verification plan;
- exact source artifacts and retrieval times;
- exact Checkout JWT versions and their digests;
- imported revocation snapshot bytes, reported states, and digests;
- `legalEffect: "not-determined"`; and
- `packDigest` over the complete canonical pack material.

The pack is sensitive. It contains the raw Mandates, Receipt JWTs, Checkout JWTs, and revocation snapshots. Store and transmit it only with suitable encryption, access controls, retention rules, and lawful processing.

`verifyAp2DisputeEvidencePack` requires `expectedPackDigest` from an independently retained case record, then recomputes the Pack digest, every Checkout-version digest, every revocation snapshot digest, and the full dispute resolution. The Pack cannot establish its own identity by supplying both its bytes and the only expected digest. A positive Pack result additionally requires:

- the Pack digest to match the independently supplied expected digest;
- an exact Checkout version matching the Checkout JWT pinned by the plan;
- reported revocation coverage for both closed Mandates; and
- only `not_revoked` imported reports.

Revocation evidence is deliberately described as reported state. The profile does not define or authenticate an upstream revocation protocol. A `not_revoked` report is not proof that a Mandate was never revoked. `revoked`, `unknown`, missing, conflicting, or digest-invalid reports produce `unresolved`.

## Timeline rendering

`createAp2EvidenceTimeline`, `renderAp2EvidenceTimelineHtml`, `renderAp2EvidenceTimelineMarkdown` and `renderAp2EvidenceTimelineCsv` require the same independent expected Pack digest and recompute verification internally. They do not accept a caller-provided verification report. The timeline sorts Checkout versions, source retrievals, reported revocation checks, and the final resolution deterministically. The HTML renderer escapes every displayed value and emits a self-contained report with a restrictive content security policy.

Since 2.1.0 the timeline also exports for tickets and spreadsheets. The Markdown rendering carries the Pack format, transaction, status, the non-binding notice, a timeline table, the issue list, the Pack digest, the retained anchor, the report digest and the legal effect, and escapes every value with the same escaper as the CasePack Markdown report. The CSV rendering has one RFC 4180 row per event (`transactionId`, `verificationStatus`, `occurredAt`, `eventType`, `label`, `state`, `digest`, `sourceRefs`, `legalEffect`), quotes every cell, neutralizes spreadsheet formulas the way the CasePack coverage CSV does, and ends lines with CRLF. Neutralizing prefixes a `'` to any cell that would start a formula, including the roughly 1 in 64 base64url transaction IDs that begin with `-`; strip one leading `'` from `transactionId` before joining the CSV to merchant or processor records. The JSON and Markdown renderings keep the exact value.

The timeline contains identifiers, times, states, digests, and source references. It never embeds raw Mandates, Receipts, Checkout JWTs, payment instruments, risk data, disclosures, snapshot bytes, or provider exception text.

## Re-verify retained Packs

A package upgrade can change the verdict for a retained Pack, because verification re-derives the resolution under the current gates. `verifyAp2DisputeEvidencePacks` and `mandatebound ap2-dispute batch` re-verify up to 100 retained Packs at once, each against its own independently retained digest, and report each Pack's status in input order:

```json
{"packs": [{"id": "case-2026-0142", "pack": {"schemaId": "MandateBoundAp2EvidencePack/v1"}, "expectedPackDigest": "sha256:<64-hex-characters>", "previousStatus": "verified"}]}
```

Here `pack` stands for the whole retained Pack, or the `{ok: true, result}` envelope that `pack` printed. Each item reports `status` (`verified`, `unresolved`, or `invalid` for a Pack that is not well formed), the digest, anchor, Checkout-version and revocation fields, the sorted issue codes of the verification and its embedded resolution, and the full verification report. When `previousStatus` is given, `statusChanged` says whether the status moved. The `MandateBoundAp2EvidencePackBatch/v1` document adds a summary and a `batchDigest` over the items in input order. A malformed batch is rejected with a fixed message that never echoes input; one malformed Pack never throws. The CLI reads the whole batch as one document under the 17 MiB `ap2-dispute` input cap, so 100 Packs fit in one run only when they average under about 170 KiB each; split larger sets across runs, or call the library function, which has no document cap.

## Payment reconciliation

The resolver binds the closed Payment Mandate to the Checkout only through `transaction_id`, the hash of the exact Checkout JWT. AP2 asks that a Payment Mandate be appropriately scoped to its Checkout without defining the comparison, so the resolver does not compare the paid amount, currency or payee with the Checkout. `reconcileAp2DisputeEvidencePack` and `mandatebound ap2-dispute reconcile` add that comparison as a separate review signal:

| Check | Compares |
| --- | --- |
| `payee_matches_checkout_merchant` | closed `payee.id` with the Checkout `merchant.id` |
| `currency_matches_checkout` | closed `payment_amount.currency` with the Checkout `currency` |
| `amount_matches_checkout_total` | closed `payment_amount.amount` with the Checkout's single `total` entry, only when the currencies match |

Each check is `matched`, `mismatched` or `not_comparable`. The checks read only claims verified inside the Pack, and only when its digest and retained anchor match and its resolution is `evidence_verified`; otherwise every check is `not_comparable`. A Checkout without a merchant, or without exactly one `total` entry, is `not_comparable` for that check. The `MandateBoundAp2PaymentReconciliation/v1` document carries the states, a `consistent`, `inconsistent` or `not_comparable` summary, the verification status and report digest, and a `reconciliationDigest`. It never carries amounts, identifiers, items, instruments or tokens. It is a review signal, not a resolution gate and not a dispute outcome: a mismatch never changes the resolution or the Pack verification.

## Retrieval contract

`resolveAp2DisputeEvidence` accepts caller-supplied `Ap2DisputeEvidenceRetriever` implementations. Each retriever declares a source ID and AP2 role, then receives the pinned profile ID, transaction ID, evaluation time, and optional abort signal.

The core performs no built-in network access. The adapter owner is responsible for endpoint authentication, authorization, privacy, rate limits, retention, and transport security. Possession of a transaction ID is not retrieval authority.

| Artifact | Eligible source roles |
| --- | --- |
| Checkout Mandate and Receipt | Shopping Agent, Merchant |
| Payment Mandate and Receipt | Shopping Agent, Credential Provider, Network, Merchant Payment Processor |

Provider failures and configured empty responses fail closed. Byte-identical copies are deduplicated while retaining every eligible source reference. Different exact bytes for one required artifact are conflicting. There is no last-response-wins selection.

## CLI

Resolve already materialized evidence:

```bash
mandatebound ap2-dispute resolve --input ap2-dispute-input.json
```

Seal a sensitive Evidence Pack:

```bash
mandatebound ap2-dispute pack --input ap2-pack-input.json > ap2-pack.json
```

Retain `result.packDigest` from that output in a separate trusted case record before the Pack enters untrusted storage.

Independently verify it:

```bash
mandatebound ap2-dispute verify --input ap2-pack.json --expected-pack-digest "sha256:<64-hex-characters>"
```

Render a metadata-only review timeline:

```bash
mandatebound ap2-dispute render --input ap2-pack.json --expected-pack-digest "sha256:<64-hex-characters>" --format html > ap2-timeline.html
```

`--format markdown` and `--format csv` print the same timeline for a ticket or a spreadsheet.

Re-verify a set of retained Packs, and compare a payment with its Checkout:

```bash
mandatebound ap2-dispute batch --input retained-packs.json
mandatebound ap2-dispute reconcile --input ap2-pack.json --expected-pack-digest "sha256:<64-hex-characters>"
```

`pack` confirms the bounded container shape and seals its exact material. Its standard `{ok,result}` output can be passed directly to `verify` and `render`. Those commands require the separately retained digest; deriving the expected value from the untrusted Pack at verification time defeats the identity anchor. Resolver and Pack verification gaps use the conflict exit class. Invalid container shapes use the invalid-input exit class.

The AP2 dispute CLI accepts at most 17 MiB of JSON input so a compact library-produced Pack within the 16 MiB canonical Pack bound can complete `pack -> verify -> render`. `casepack`, `case-report` and the operator actions also read up to 17 MiB; the other commands keep a 4 MiB document cap. The [CLI reference](CLI.md#input-limits) lists every limit.

## Library

Library consumers can import:

```text
@oonyl/mandatebound/ap2-dispute
```

The v1.2 entry points are:

- `assembleAp2DisputeEvidence`
- `resolveAp2DisputeEvidence`
- `packAp2DisputeEvidence`
- `verifyAp2DisputeEvidencePack`
- `createAp2EvidenceTimeline`
- `renderAp2EvidenceTimelineHtml`
- `renderAp2EvidenceTimelineMarkdown` and `renderAp2EvidenceTimelineCsv` (2.1.0)
- `verifyAp2DisputeEvidencePacks` (2.1.0)
- `reconcileAp2DisputeEvidencePack` (2.1.0)
- `AP2_DISPUTE_CONSTRAINT_SUPPORT` (2.1.0)

Published schemas cover the resolution, sensitive Pack, and Pack-verification report under `schemas/v1.2`.

Library calls pass `{ expectedPackDigest }` as the second argument to Pack verification, reconciliation and every timeline function; a batch item carries its own `expectedPackDigest`. A missing, malformed, or mismatched anchor produces `unresolved`.

## Verification evidence

The test suite contains synthetic direct and delegated Mandates, malformed and adversarial cases, pack-forgery cases, schema validation, CLI coverage, and a frozen vector generated with the official AP2 v0.2.0 Python SDK at the pinned commit. Passing these fixtures supports only this bounded profile. It does not establish general AP2 conformance or production readiness.

## Fail-closed boundaries

At least the following remain unresolved:

- missing or conflicting artifacts;
- malformed, oversized, or noncanonical compact representations;
- invalid signatures, disclosures, delegation links, issuers, pins, or times;
- empty caller-owned trust identifiers;
- missing, unsupported, or violated constraints;
- constraint disclosures withheld by the presenting agent;
- an invalid Checkout shape or merchant signature;
- a Checkout hash, open-Checkout reference, or transaction mismatch;
- a Receipt schema or terminal-Mandate reference mismatch;
- invalid source roles, future retrieval times, or provider failures;
- a forged Pack, Checkout-version digest, or revocation snapshot digest;
- a missing or mismatched independently retained Pack digest;
- missing Checkout-version binding;
- missing reported revocation coverage; or
- reported `revoked` or `unknown` state.

`unresolved` is not an accusation of fraud, invalid consent, or legal breach.

## Compatibility and limits

This is an additive minor release. Native v1 schemas, bundle roots, rulebook semantics, engine decisions, protocol version `1.0.0`, and engine version `1.0.0` remain unchanged. v1.1 CasePacks and evidence-import functions remain available.

The resolver is not a hosted claims service, payment operator, refund mechanism, chargeback engine, insurer, compliance certification, or legal adjudicator. It does not establish complete upstream history.
